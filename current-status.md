## Project shape

This is a Python command-line utility for Windows that uses WizTree or WinDirStat exports. `python drive_cleaner.py` opens a guided menu for scanning, analysis, and backup management. Automated WinDirStat scanning requires 2.6.0 or later. It is not yet a signed installer or desktop GUI. The primary user flow is scan → review report → choose files/folders → choose a backup or skip it → confirm → cleanup; restore is available when a verified backup was made.

## Current capabilities

- Guided prompts use the same plain-language terms from scanning through review, file/folder selection, cleanup-plan confirmation, and recovery-backup management. The picker explicitly says you can choose individual files, folders, or both, and warns that choosing a folder may also clean eligible contents inside it. Enter `D` to browse scan entries that the summary grouped under a folder; the paginated browser supports filtering and adds only exact selected paths to the cleanup plan. In that browser, `D` keeps its picks and returns to the main list; `B` returns without adding picks from the current browse, while preserving earlier main-list selections. Browsing follows the selected review group, and skipped stale, project, or linked entries are explained. Reports keep their compact, non-overlapping folder totals.
- Guided single-command menu starts with an original ASCII space-map welcome screen, a short scan-to-clean workflow, and a clear statement that scans and reviews do not delete files; menu choices remain visible immediately below. The menu covers scanning, previous-scan review, and backup management; scan option prompts retry invalid yes/no and numeric input and support explicit cancellation. The review menu, direct analyzer, and backup confirmations cancel cleanly on Ctrl+C or end-of-input.
- Project detection protects caches under VS Code `.vscode` workspace folders, alongside `*.code-workspace` files, and in folders with AI project guidance or settings such as `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, `SKILL.md`, `.cursorrules`, `.cursor`, `.claude`, `.github`, or `copilot-instructions.md`, including nested cleanup-plan checks. Shared guidance/settings at the profile root do not make the entire user profile a project. The profile-level `.vscode` extensions directory remains protected.
- Agent/editor settings folders `.claude`, `.cursor`, `.gemini`, `.github`, `.opencode`, and `.windsurf` are excluded from cleanup suggestions because they can hold authentication, user settings, history, and project instructions; close names such as `.cursorBackup` still follow normal review rules.
- Scans started with the direct `scan.py` command are saved into the same previous-scan list; completion points users to the guided menu instead of suggesting a second analyzer command.
- The previous-scan picker accepts files only; missing or unreadable scans produce a clear message and return the user to scan selection instead of a traceback.
- WizTree and WinDirStat 2.6+ scanning, selectable at the prompt or with `--app`; both auto-detected through environment variables, local folders, common install paths, and `PATH`. Official portable builds are supported when the executable is located or configured. Scans accept a drive root or existing absolute local folder.
- WizTree exports use documented CLI options for standard or fast full-drive scanning, file/folder rows, allocation sorting, drive capacity, and export depth. Automatic mode uses fast scanning for elevated whole-drive scans and standard mode otherwise; both `C:` and `C:\` are recognized as drive roots. Folder scans use standard mode, and explicit fast-scan requests for folders are rejected before WizTree launches. The scan mode is encoded in the export name and the review report carries the access limitation forward. The guided flow asks for the target before offering whole-drive scan modes, then exposes file rows and depth. Discovery prefers a paired `WizTree64.exe` when `WIZTREE_PATH` names the 32-bit launcher so completion is tied to the export worker. WinDirStat `/SaveTo` uses the app's saved filters and scan settings. WinDirStat also supports separate load and duplicate-report modes; Drive Cleanr keeps cleanup scans on the CSV tree-export mode.
- Cleanup category and protection rules match whole Windows path components (or adjacent component sequences); more-specific rules win and equally specific overlaps use the more cautious tier. Project detection recognizes common manifests/build files, Git metadata and markers (`.git`, `.gitignore`, `.gitattributes`), project guidance files, `.idea`/`.vs` workspaces, Unreal/Godot/Unity project markers, and Visual Studio solution/project suffixes, and user profile roots; shared editor, AI-assistant, or Node metadata at the user-profile root does not shield the whole profile. Unreadable directories are conservatively omitted.
- Automatic crash-dump candidates are restricted to known direct diagnostic paths beneath the drive's `Windows` directory; they appear in the caution tier because dumps can help troubleshoot crashes and may contain memory data. Identically named archive and project paths do not match.
- When broad and specific cleanup rules both match, the most specific path rule wins so global Gradle, Cargo, NuGet, and Go caches retain their caution-oriented package-manager labels.
- Chrome on-device model suggestions require a Chrome User Data path, stay in the caution tier, warn that Chrome may re-download the model, and reject obsolete lower-risk candidate labels; NVIDIA App update artifacts require a known ProgramData updater path and stay in the caution tier.
- IndexedDB cleanup candidates require a recognized Chrome or Edge User Data profile path; arbitrary IndexedDB folder names are left unclassified.
- Generic cache/log/GPU-cache labels state that folder names are only clues, remain in the caution tier, and tell users to inspect the exact location and contents.
- Known VS Code `CachedExtensionVSIXs`, `CachedData`, `Cache`, and `Crashpad` folders under `%APPDATA%\Code` get app-specific caution labels; nested cache-named folders under `User` still use generic caution labels.
- Only known Windows, user-profile, or configured `TEMP`/`TMP` roots are classified as temporary files; unrelated folders named `Temp` or `Tmp` stay in the caution tier.
- Cargo install build output and Chocolatey staging inside known temp roots receive specific caution labels so compiled executables and installer payloads are not presented as generic temporary files.
- Bcut (`BCUT`) cache is no longer labeled as lower-risk disposable data; if matched by the generic cache rule, it appears only as a caution item for exact-path review.
- Codex protection covers `.codex`, legacy `.codex-old` profiles, Microsoft Store package folders beginning `OpenAI.Codex_`, and `AppData\Roaming\Codex` profiles discovered in the shared candidate report.
- WinDirStat CSV parsing using its full path, logical size, physical size, and hexadecimal directory attributes plus file/folder counts.
- Candidate file/folder types are verified against the current filesystem. Missing WinDirStat type metadata uses the current path type; conflicting exported types and paths crossing junctions, symbolic links, or unreadable path components are omitted and counted. Reports and candidate lists show the source scan export timestamp and recommend rescanning if paths may have changed.
- Windows reserved device names are rejected in imported scan paths and ZIP restore targets, including the superscript `COM¹`–`COM³` and `LPT¹`–`LPT³` aliases.
- `pagefile.sys`, `swapfile.sys`, and `hiberfil.sys` are excluded by filename from scan candidates and imported cleanup plans.
- Generated cleanup scripts recheck project markers in target ancestry before backup and immediately before removal; folder cleanup also rescans descendants after backup verification and before the first removal, stopping if a project marker, protected path, or reparse point appeared during review. Unreadable ancestor folders fail closed, including for single-file targets.
- Cleanup progress reports the percentage and amount of bytes hashed within a large selected file, in addition to the selected-file count; integrity hashes and locked-handle rechecks are retained.
- Reports show when listed files or folders are inside another listed folder, explain that folder rows show full size, and count nested space only once across review levels.
- Analyzer progress shows the percentage of the scan CSV read instead of a technical row count, reaching 100% after parsing completes.
- Selected directory roots are removed only with a non-recursive empty-directory operation after child cleanup, preserving any new data that appears during the cleanup window.
- When a WinDirStat export lacks volume statistics, show current local drive capacity/free space and label it as checked at analysis time.
- English-language menus, prompts, reports, and reference documentation; localized WizTree headings remain supported, and localized WinDirStat headers are accepted only after its documented CSV layout and sample values validate.
- The guided review labels each listed entry File or Folder, shows its exact path, and explains that only entries included in the scan can be selected. Users choose numbered files/folders, choose all displayed entries, or cancel. The generated plan shows each selected item's type and path, and contains only the user's selections; direct CLI-generated plans retain the run-time picker. When the menu is already running as administrator, it offers to run a newly saved plan in that same session; the default is to leave it saved, and the plan still requires its own confirmation.
- Process-aware scan progress and configurable timeouts; transient export-stat access errors do not abort scanning. Scanner output stays under `data/.incomplete/` until the process exits and the CSV passes validation, then moves into the completed-scan list. Failed exports are removed only after the scanner is confirmed stopped; otherwise they remain isolated from review and retention cleanup. Prior scans and reviewed cleanup scripts stay until explicit cleanup. Retention cleanup removes a default `.clean.ps1` plan only alongside its pruned scan export; custom plans and unrelated PowerShell files are preserved.
- Scanner success requires a stable, readable CSV with recognized path and size columns, or a validated WinDirStat 2.x row from its documented column order; WizTree's generated-note preface is accepted without loading the whole export.
- The scan runner reads WinDirStat's executable version when available, rejects detected versions below 2.6 before launch, and warns but proceeds when version metadata is unavailable.
- `.gitignore` excludes the complete `data/` tree, backup folders, generic CSV exports, `clean_*.ps1`, and default `*.clean.ps1` plans. `git check-ignore` verified completed and incomplete scan paths, backup manifests, and the default generated-plan filename.
- Scan creation avoids occupied export names without overwriting old scans. Scan creation and retention cleanup refuse storage paths that cross symlinks, junctions, or other reparse points.
- Full scans include file rows so large individual files are visible.
- English interface with English/Chinese WizTree CSV-header compatibility (including a generated-note preface) plus WinDirStat 2.x CSV exports with localized-header validation; size threshold, JSON output, deduplicated candidate-list export, and interactive TUI.
- High/medium/low cleanup classifications, safety exclusions, and generated scripts for selected tiers. Downloads, Microsoft Store per-user package data, cloud/container CLI profiles, OneDrive roots (including `OneDrive - <organization>`), recovered previous-installation trees, Windows Update downloads, Windows recovery staging, update logs, Service Worker data, Codex/agent settings, and container machine state are excluded from direct cleanup. Candidate rules match exact path components or adjacent component sequences; only explicitly named dump files accept dotted filenames. Candidates under detected project roots or folders containing `.drive-cleanr-protect` are omitted; plan generation revalidates local non-root paths, reparse-point status, exclusions, project markers, selected priority, and exact rule labels for imported candidate data. Known temporary roots are omitted so qualifying contents can be selected individually; temporary-folder candidates carry an installer/build review warning, with process warnings for common browsers, editors, Java, Conda/Mamba/Pixi, Node.js, Rust, Go, .NET, Windows servicing, and package managers.
- Candidate list exports deduplicate overlapping parent/child paths across risk tiers and label the risk tier without calling any candidate guaranteed safe.
- Generated cleanup plans and candidate reports refuse to overwrite an existing file. Before confirmation, cleanup plans preview up to 12 direct children per selected folder and stop safely if the preview cannot be read.
- Generated cleanup plans accept `-PreviewOnly` to run current safety checks and list every eligible file or folder with its exact path and file-data size. This mode bypasses backup and removal prompts, creates no backup, and removes nothing; a later cleanup repeats its checks because paths can change.
- Before checking each cleanup item, generated plans say which item is being checked and that nothing has been removed yet. Project checks and folder reviews print a visible count every 100 entries; project-file and protected-data checks now do the same during the classification passes that run after inventory and before the first file-content count. File-content checks and removals print a count every 100 files. The full inventory and first content check finish before that folder's cleanup begins.
- Generated scripts advise least-privilege execution and let users select numbered targets, select all, or cancel. Plan indices stay attached to their original targets when another target has disappeared. Before prompting or backing up, and again after backup and immediately before removal, they recheck target type and every existing ancestor for reparse points. Interactive users can choose a verified backup; if chosen, missing, incomplete, or failed backups abort cleanup. Declining during interactive cleanup requires a distinct typed confirmation. Reviewed noninteractive `-Force` cleanup creates no backup unless `-Backup` is explicitly supplied. Plans find `backup.py` beside the plan or in the project folder when backup is enabled. Scripts preserve nested protected data and project roots, and return a failure code if any selected cleanup fails.
- Directory cleanup preserves nested excluded locations, detected project roots, and candidates classified at a more cautious tier when a user selects a parent, unless the user explicitly selects that nested candidate too; selected nested candidates are shown in the preview. The plan now explains that folder selection includes other contents that are not separate scan suggestions, and that its preview shows at most 12 direct items rather than every removal target. It refuses to clean directory trees containing reparse points. Every enumerated descendant and its nested ancestors are reopened and rechecked immediately before removal to stop a junction introduced after the cleanup checks. Files are snapshotted by size, last-write time, and SHA-256 before cleanup verification, then rehashed immediately before removal; changed contents are left in place even if size and timestamp are preserved. Reports explain that nested space is counted once across review levels while each folder row shows its full size.
- Final cleanup removal now uses Windows file handles pinned to the reviewed file identity and hash, with a shared byte-range lock preventing ordinary file-handle writes during the final hash and deletion and parent paths locked only for the brief deletion step. Windows does not apply byte-range locks to memory-mapped writes. A junction or replacement injected at the deletion boundary is rejected; empty folders are deleted by handle, and read-only files retain the previous cleanup support.
- Backups support files, direct directory copies, compressed directories, manifests, listing, restore, and deletion. New manifests include a versioned integrity format that hashes named Windows data streams as well as default file contents; large stream-bearing folders use direct copies because ZIP cannot preserve those streams. Backup sizes include stream bytes and copy verification fails closed if the destination drops or changes them. Large backup sizing, file copying, ZIP creation, hashing, archive checks, and Robocopy waits report periodic English progress; `--json` creation keeps its manifest on stdout and sends progress to stderr. Older manifests remain restorable with a warning, but cannot verify files or trees that currently contain unrecorded named streams. Backup creation rejects duplicate or overlapping selected paths before creating storage; manifest verification and restore reject duplicate or overlapping paths before writing. The backup list displays completed/partial status, shows the saved backup location, and escapes terminal control characters from manifest text; discovery and direct operations reject malformed or redirected manifests, and deletion refuses backup trees containing reparse points. Partial copy/archive failures include machine-readable error details and are labeled incomplete in console output.
- Bulk backup cleanup displays the exact saved-backup snapshot, requires typing `DELETE`, and has a separate `--yes` bypass for deliberate unattended use.
- Restore validates all backup payloads before writing. ZIP preflight validates every member path, CRC, and timestamp before restoring any entry, so malformed later metadata cannot leave an earlier member partially restored. Files restored from direct or ZIP backups are copied and checked in a same-directory staging file before an atomic destination replace/create. Directory-copy restores recheck the source and destination for links immediately before Robocopy starts. Existing destination files are preserved by default; file restores skip conflicts, and directory/ZIP restores add missing files while reporting skipped conflicts. Interactive confirmation or explicit CLI `--yes` approval enables overwriting.
- Backup creation rejects drive roots and non-local or non-normalized source paths before creating backup storage.
- Backup creation also rejects sources reached through reparse points and backup roots that cross junctions; unique backup directories cannot be reused on an ID collision.
- New file, directory-copy, and ZIP backups record SHA-256 integrity fingerprints; restore checks all payloads before writing any destination. ZIP creation fingerprints the source and exact streamed archive contents so concurrent source changes mark the backup partial. Older manifests without hashes remain supported with size/structure checks and a warning. Same-size backup mismatches at creation mark the backup partial so cleanup cannot proceed.
- `backup.py verify --id <id>` checks saved payloads and current source content, with optional `--paths` to limit the check. Older backups without source fingerprints fail closed for this check.
- Large directory archives use ZIP64 and include hidden entries; restore validates all manifest targets before writing, refuses traversal/network/device targets and reparse-point redirection, and restores saved Windows attributes.
- Mock safety tests cover malformed paths, PowerShell quoting, backup failure, scan timeouts, and generated-script preservation.
